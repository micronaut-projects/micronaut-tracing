The OpenTelemetry context of a request (the current span) follows the request across threads through Micronaut's https://docs.micronaut.io/latest/guide/#contextPropagation[context propagation]: the tracing filters and the `@NewSpan` and `@WithSpan` interceptors add it to the `PropagatedContext`, and every hop that propagates the `PropagatedContext` makes it current again on the new thread, then restores the previous context of that thread when the work is done.

The following execution models are covered by tests, in both propagation modes unless stated otherwise:

|===
| Execution model | Supported | Notes

| `@ExecuteOn(TaskExecutors.VIRTUAL)`, `@ExecuteOn(TaskExecutors.BLOCKING)`, `@ExecuteOn(TaskExecutors.IO)`
| Yes
| `BLOCKING` uses virtual threads when they are available (Java 21+).

| `@NewSpan` / `@WithSpan` methods on virtual threads
| Yes
|

| An executor used manually with `PropagatedContext.wrapCurrent(...)` or `PropagatedContext.get().wrap(...)`
| Yes
| For example a virtual thread executor created with `Executors.newVirtualThreadPerTaskExecutor()`.

| `ExecutorService` beans, `@Async` methods (`void` and `CompletableFuture`)
| With `micronaut-context-propagation`
| The `micronaut-context-propagation` module instruments the `ExecutorService` beans (including the executor of `@Async`, `scheduled` by default). Without it the task runs without the context of the caller.

| `CompletableFuture.supplyAsync(task, executor)`
| With an instrumented executor
| `executor` must be an instrumented `ExecutorService` bean, or the task must be wrapped.

| `CompletableFuture.supplyAsync(task)` and other tasks on the common `ForkJoinPool`
| No, unless wrapped
| The common pool is not instrumented: wrap the task with `PropagatedContext.wrapCurrent(task)`.

| Reactor `publishOn` / `subscribeOn` (`boundedElastic`, `parallel`) and `flatMap` concurrency, in controllers and in reactive `@NewSpan` methods
| Yes
| The HTTP client reads the context from the Reactor context. `Span.current()` after a thread switch requires `micronaut-reactor`, which instruments the schedulers; otherwise use `OpenTelemetryReactorPropagation.currentContext(contextView)`.

| Kotlin coroutines: `delay`, `withContext(Dispatchers.Default / IO / IO.limitedParallelism(n))`, suspend `@NewSpan` methods and HTTP clients
| Thread-local mode only
| See the scoped-value mode below.

| Coroutines launched in a custom `CoroutineScope`
| With the propagated context element
| Add the context with `KotlinCoroutinePropagation.addPropagatedContext(coroutineContext, propagatedContext)`. A scope created without it, such as `CoroutineScope(Dispatchers.Default)`, has no trace context.

| `StructuredTaskScope`
| Not tested
| Structured concurrency is a preview API in Java 25 (it requires `--enable-preview`). Fork subtasks with a task wrapped with `PropagatedContext.wrapCurrent(...)`.
|===

The threads of executors and Reactor schedulers are left without the context of the request once the work handed to them is done.

== The scoped-value propagation mode

With `micronaut.propagation: scoped-value` (Micronaut Framework 5.3+), the propagated context is bound with a `ScopedValue` for the extent of a callback instead of a thread local. The OpenTelemetry tracing works in this mode: the HTTP server and client, `@NewSpan`, `@ExecuteOn`, virtual threads, the instrumented executors and Reactor behave as in the default `thread-local` mode, and the OpenTelemetry context is still made current on the thread for the extent of each callback, so `Span.current()` and the MDC correlation keep working.

CAUTION: Kotlin suspend functions do not work in the scoped-value mode with Micronaut Framework 5.3: the coroutine context element of Micronaut opens a scope, which the scoped-value mode doesn't support, so dispatched coroutines fail. Use the default `thread-local` mode with coroutines. The Kafka consumer instrumentation only makes the record context current with the OpenTelemetry API in this mode, so `@Async` methods called from a listener don't continue the trace of the record.
