== Ordering custom server filters

OpenTelemetry HTTP server tracing runs in the Micronaut `ServerFilterPhase.TRACING` phase.
If a custom server filter reads from or writes to the current OpenTelemetry span, order the filter after the tracing phase so the server span is already current in request and response filters.

== Filtering HTTP spans

It may be useful to exclude health-checks and other HTTP requests to your service.
This can be achieved by adding a list of regular expression patterns to your configuration:

.Filtering HTTP request spans
[configuration]
----
otel:
  exclusions:
    - /internal/ping
    - /static/.*
----

The requests to the Micronaut management endpoints (`/health`, `/info`, `/prometheus`...) are excluded from the HTTP server tracing by default. Set `tracing.opentelemetry.http.server.exclude-management-endpoints` to `false` to trace them, or list the ids of the endpoints to trace in `tracing.opentelemetry.http.server.traced-management-endpoints`. To sample requests rather than exclude them, see the sampling rules and rate limit in <<performance, Performance Tuning>>.

== Add HTTP Headers into request spans

If you want you can add additional Http Headers inside your span objects. You can specify different headers for client request, client response, server request and server response.

.Adding HTTP Headers into request spans
[configuration]
----
otel:
  http:
    client:
      request-headers:
        - X-From-Client-Request
      response-headers:
        - X-From-Client-Response
    server:
      request-headers:
        - X-From-Server-Request
      response-headers:
        - X-From-Server-Response
----

== Source code attributes

The server span of a request routed to a controller method has the https://opentelemetry.io/docs/specs/semconv/registry/attributes/code/[`code.function.name`] attribute: the fully qualified name of the method, for example `com.example.BookController.list`, so that the span links to the code that handled the request. The spans of the requests that match no route (for example a `404`), of the error routes and of the static resources have no code attributes. The value is computed once per route, and the method name of a Kotlin function with an inline class or `kotlin.Result` in its signature is its source name rather than its mangled JVM name when the class is compiled with the `micronaut-tracing-opentelemetry-annotation` processor.

`code.function.name` replaces the deprecated `code.namespace` and `code.function` attributes. To also add them, for a backend that does not support `code.function.name` yet, or to disable the code attributes, set the following properties:

.Configuring the source code attributes
[configuration]
----
tracing:
  opentelemetry:
    http:
      server:
        code-attributes:
          enabled: true
          legacy-attributes: true
----

|===
| Property | Default | Description

| `tracing.opentelemetry.http.server.code-attributes.enabled`
| `true`
| Whether the HTTP server spans have the `code.function.name` attribute.

| `tracing.opentelemetry.http.server.code-attributes.legacy-attributes`
| `false`
| Whether the deprecated `code.namespace` (the class name) and `code.function` (the method name) attributes are also added.
|===

The attributes are added by the api:tracing.opentelemetry.instrument.http.server.HttpServerCodeAttributesExtractor[] bean, an `AttributesExtractor` contributed with the ann:tracing.opentelemetry.instrument.http.server.MicronautHttpServerTelemetryFactory.Server[] qualifier (see _Customizing HTTP instrumentation_ below). Replace it with an `AttributesExtractor` bean annotated with `@Replaces(HttpServerCodeAttributesExtractor.class)`.

== HTTP metrics

The HTTP server and client instrumenters can record the OpenTelemetry `http.server.request.duration` and `http.client.request.duration` histograms. Recording them costs an allocation of listener state, a `Context` copy and an attribute merge on every request, even when the metrics are dropped, so they are only recorded when OpenTelemetry exports metrics: when `otel.metrics.exporter` is set to an exporter other than `none` (Micronaut's default is `none`), or when a `MetricReader` is registered on the SDK meter provider, for example with an `OpenTelemetryBuilderCustomizer`. The check is made against the `MeterProvider` of the `OpenTelemetry` bean when the instrumenters are built, so it also covers an `OpenTelemetry` instance provided by the application or the OpenTelemetry Java agent.

To override the detection, set the following properties:

.Enabling or disabling the HTTP metrics
[configuration]
----
tracing:
  opentelemetry:
    http:
      server:
        metrics:
          enabled: true
      client:
        metrics:
          enabled: false
----

|===
| Property | Default | Description

| `tracing.opentelemetry.http.server.metrics.enabled`
| `true` only when metrics are exported
| Whether the HTTP server instrumenter records `http.server.request.duration`.

| `tracing.opentelemetry.http.client.metrics.enabled`
| `true` only when metrics are exported
| Whether the HTTP client instrumenter records `http.client.request.duration`.
|===

These properties only control the default metrics. `OperationMetrics` beans that you contribute with the ann:tracing.opentelemetry.instrument.http.server.MicronautHttpServerTelemetryFactory.Server[] or ann:tracing.opentelemetry.instrument.http.client.MicronautHttpClientTelemetryFactory.Client[] qualifier (see below) are always applied.

TIP: If the application also uses https://micronaut-projects.github.io/micronaut-micrometer/latest/guide/[Micronaut Micrometer] with its web metrics binder (`micronaut.metrics.binders.web.enabled`, enabled by default), every request is timed twice: once by OpenTelemetry and once by Micrometer (`http.server.requests` / `http.client.requests`). A warning is logged at startup in that case. Keep only one of them by setting `tracing.opentelemetry.http.server.metrics.enabled` / `tracing.opentelemetry.http.client.metrics.enabled` to `false`, or `micronaut.metrics.binders.web.enabled` to `false`.

== Customizing HTTP instrumentation

HTTP client and server OpenTelemetry `Instrumenter` builders can be customized by defining beans with the appropriate qualifier:

* ann:tracing.opentelemetry.instrument.http.client.MicronautHttpClientTelemetryFactory.Client[] for HTTP client instrumentation.
* ann:tracing.opentelemetry.instrument.http.server.MicronautHttpServerTelemetryFactory.Server[] for HTTP server instrumentation.

Qualified beans of type `SpanNameExtractor`, `SpanStatusExtractor`, `ErrorCauseExtractor`, `AttributesExtractor`, `ContextCustomizer`, `OperationMetrics`, `OperationListener`, and `SpanLinksExtractor` are applied when the Micronaut HTTP instrumenters are built. `SpanNameExtractor`, `SpanStatusExtractor`, and `ErrorCauseExtractor` are single collaborators and do not compose; if one already exists, replace it with ann:context.annotation.Replaces[]. `AttributesExtractor`, `ContextCustomizer`, `OperationMetrics`, `OperationListener`, and `SpanLinksExtractor` beans are additive contributors.

NOTE: Custom extractors, customizers, metrics, listeners, and span link extractors can add request, response, exception, and application data to telemetry. Redact secrets such as authorization headers, cookies, API keys, tokens, and personally identifiable information before exporting telemetry.
