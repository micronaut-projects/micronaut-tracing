Most tracing backends receive the OpenTelemetry Protocol (OTLP), so one exporter covers them all. Add the OTLP exporter:

dependency:opentelemetry-exporter-otlp[scope="implementation", groupId="io.opentelemetry"]

and enable it. The exporter is configured with the `otel.exporter.otlp.*` properties of OpenTelemetry autoconfigure, which Micronaut reads from its environment, so they can be set in `application.yml`, as system properties or as environment variables (`OTEL_EXPORTER_OTLP_ENDPOINT`...):

[configuration]
----
otel:
  traces:
    exporter: otlp
  exporter:
    otlp:
      endpoint: http://localhost:4318
      protocol: http/protobuf
----

[cols="1,3"]
|===
|Property |Description

|`otel.exporter.otlp.protocol`
|`grpc` or `http/protobuf`. The OpenTelemetry SDK defaults to `grpc`. By convention, receivers listen on port `4317` for gRPC and `4318` for HTTP.

|`otel.exporter.otlp.endpoint`
|The base URL of the receiver. With `http/protobuf`, the exporter appends the signal path (`/v1/traces`). `otel.exporter.otlp.traces.endpoint` sets the full URL of the traces endpoint instead, used as is.

|`otel.exporter.otlp.headers`
|Headers sent with each export, typically for authentication. `otel.exporter.otlp.traces.headers` applies to the traces only.

|`otel.exporter.otlp.compression`
|`gzip` or `none`.

|`otel.exporter.otlp.timeout`
|The export timeout, `10s` by default.
|===

Headers can be written in the OpenTelemetry format (`api-key=secret,other=value`) or as nested configuration, which keeps the case of the header names:

[configuration]
----
otel:
  exporter:
    otlp:
      headers:
        Authorization: Bearer your-token
----

Do not commit credentials: resolve them from the environment with a property placeholder, or set `OTEL_EXPORTER_OTLP_HEADERS` in the deployment.

TIP: In production, consider sending the telemetry to an https://opentelemetry.io/docs/collector/[OpenTelemetry Collector] next to the application, and let the Collector batch, filter and forward it to one or more backends.

The metrics and logs exporters default to `none`. Set `otel.metrics.exporter` and `otel.logs.exporter` to `otlp` to export them too, to backends that accept them.

== Jaeger

Jaeger receives OTLP natively (Jaeger 1.35 and later, and Jaeger v2) on ports `4317` and `4318`. OpenTelemetry no longer publishes a Jaeger exporter.

[configuration]
----
otel:
  traces:
    exporter: otlp
  exporter:
    otlp:
      endpoint: http://localhost:4317
      protocol: grpc
----

For a local Jaeger: `docker run --rm -p 16686:16686 -p 4317:4317 -p 4318:4318 jaegertracing/jaeger:latest`, then open the UI at http://localhost:16686. See also <<migrationFromOpenTracing, Migrating from OpenTracing>>.

== Zipkin

The Zipkin server does not receive OTLP. Run an OpenTelemetry Collector with the `otlp` receiver and the `zipkin` exporter, and point the application at the Collector. The OpenTelemetry Zipkin exporter is discontinued, see <<exporters, OpenTelemetry Exporters>>.

== Grafana Tempo and the Grafana LGTM stack

Tempo receives OTLP once the `otlp` receiver is enabled in its distributor configuration, on ports `4317` and `4318`. For local development, the `grafana/otel-lgtm` image runs an OpenTelemetry Collector with Tempo, Prometheus, Loki and Grafana: `docker run --rm -p 3000:3000 -p 4317:4317 -p 4318:4318 grafana/otel-lgtm`.

[configuration]
----
otel:
  traces:
    exporter: otlp
  metrics:
    exporter: otlp
  logs:
    exporter: otlp
  exporter:
    otlp:
      endpoint: http://localhost:4318
      protocol: http/protobuf
----

For Grafana Cloud, use the OTLP endpoint and the `Authorization: Basic ...` header shown in the OpenTelemetry section of the Grafana Cloud portal, with `http/protobuf`.

== Datadog

The Datadog Agent receives OTLP when OTLP ingestion is enabled, for example with the environment variables `DD_OTLP_CONFIG_RECEIVER_PROTOCOLS_GRPC_ENDPOINT=0.0.0.0:4317` and `DD_OTLP_CONFIG_RECEIVER_PROTOCOLS_HTTP_ENDPOINT=0.0.0.0:4318` (or the `otlp_config` section of `datadog.yaml`). The application sends to the Agent, which holds the API key, so no header is needed:

[configuration]
----
otel:
  traces:
    exporter: otlp
  exporter:
    otlp:
      endpoint: http://datadog-agent:4317
      protocol: grpc
----

The `dd-java-agent` is not needed and should not be combined with the OpenTelemetry SDK of Micronaut Tracing, or the requests are traced twice. See the https://docs.datadoghq.com/opentelemetry/[Datadog OpenTelemetry documentation].

== Apache SkyWalking

The SkyWalking OAP server receives OTLP traces over gRPC, on its gRPC port (`11800` by default), when the OpenTelemetry receiver is enabled with the `otlp-traces` handler (`SW_OTEL_RECEIVER=default` and `SW_OTEL_RECEIVER_ENABLED_HANDLERS=otlp-traces`, add `otlp-metrics` and `otlp-logs` for the other signals). See the https://skywalking.apache.org/docs/[SkyWalking documentation] of your OAP version.

[configuration]
----
otel:
  traces:
    exporter: otlp
  exporter:
    otlp:
      endpoint: http://skywalking-oap:11800
      protocol: grpc
----

The SkyWalking Java agent is not needed with Micronaut Tracing.

== Honeycomb

[configuration]
----
otel:
  traces:
    exporter: otlp
  exporter:
    otlp:
      endpoint: https://api.honeycomb.io
      protocol: http/protobuf
      headers:
        x-honeycomb-team: your-api-key
----

Use `https://api.eu1.honeycomb.io` for the EU region. The dataset is the service name (`otel.service.name`, by default `micronaut.application.name`).

== Other vendors

Hosted backends follow the same pattern: an HTTPS endpoint and an authentication header. For example:

[cols="1,2,2"]
|===
|Backend |`otel.exporter.otlp.endpoint` |`otel.exporter.otlp.headers`

|New Relic
|`https://otlp.nr-data.net` (US), `https://otlp.eu01.nr-data.net` (EU)
|`api-key=<license key>`

|Elastic Observability
|The APM Server or managed OTLP endpoint of the deployment
|`Authorization=Bearer <secret token>` or `Authorization=ApiKey <api key>`

|Dynatrace
|`https://<environment-id>.live.dynatrace.com/api/v2/otlp`, with `http/protobuf`
|`Authorization=Api-Token <token>`
|===

Check the documentation of the backend for the current endpoints, the supported protocols and the signals it accepts.
